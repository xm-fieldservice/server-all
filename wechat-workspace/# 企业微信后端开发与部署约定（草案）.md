# 企业微信后端开发与部署约定（草案）

> 本文档约定的是 **“怎么开发 & 怎么部署”**，不重复业务需求。  
> 初版基于 2026-01-05 的本地环境和架构讨论，后续可按实际情况迭代。

---

## 1. 环境分层与总体原则

- **环境分层**
  - `local`：开发者本机环境（Windows + Docker）。
  - `dev`：开发/联调服务器环境。
  - `prod`：生产环境。

- **统一原则**
  - 尽量保持 **Python 版本、Postgres + pgvector 版本在各环境一致**。
  - 所有环境差异通过 **环境变量 / .env 文件** 控制，不在代码里写死。
  - 所有数据库结构变化必须通过 **迁移脚本** 执行（不直接手工改表）。

---

## 2. 本地开发环境约定

### 2.1 语言与工具

- 操作系统：Windows（PowerShell）。
- Python：3.11.x（当前为 3.11.6）。
- 包管理：`pip` + 项目级虚拟环境（推荐在各项目根目录使用 [.venv](cci:7://file:///d:/AI/ai-factory/.venv:0:0-0:0)）。

### 2.2 容器 & 数据库

- 使用 Docker / Docker Compose 管理本地服务组件。
- 当前本机已有数据库实例（供 ai-factory 和新企业微信系统共用）：
  - 镜像：`pgvector/pgvector:pg16`（Postgres 16 + pgvector）
  - 容器名：`ai-factory-pgvector`
  - 访问：`host=localhost`, `port=5433`
  - 已存在的库与账号：
    - 数据库：`rag_db`
    - 用户：`rag_user`
- 约定：
  - **内容库**：统一使用 `rag_db` 存放“笔记 / 工作记录 / 对话语料”等 entries（含三栏页面、微信通道等）。
  - 如后续需要独立业务库（工单/通知/档案基础表），在同一实例中创建新的 DB 或 Schema（例如 `ops_platform` 或 `ops` schema）。

### 2.3 本地服务运行方式

- 代码（ai-factory、wechat-backend 等）：
  - 在宿主机直接运行（非容器内开发），方便断点调试。
- 数据库等中间件：
  - 使用 Docker 容器运行（如 `ai-factory-pgvector`）。
- 本地 wechat-backend：
  - 开发时直接连 `localhost:5433` 的 Postgres 实例。
  - 先用“模拟微信请求”的 REST 接口调试数据流，再接入真正的企业微信回调。

## 3. 服务器环境约定（dev / prod）

### 3.1 基础设施

- 操作系统：优先使用 Linux（如 Ubuntu 22.04）。
- 组件建议：
  - Python 3.11.x
  - Docker + Docker Compose（如企业运维允许）
  - Nginx：作为统一入口，提供 HTTPS，反向代理到 wechat-backend。
  - Postgres 16 + pgvector（可用与本地相同镜像 `pgvector/pgvector:pg16`）
  - 可选：Redis（用于缓存/队列）

### 3.2 服务划分（逻辑）

- `ai-factory-service`：
  - 现有 AI 工厂项目，作为统一 AI 能力中心。
- `wechat-backend-service`：
  - 新的企业微信后端：
    - 接收 WeCom 回调（消息、事件）；
    - 将消息映射为统一内容条目并入库；
    - 调用 ai-factory（问一问等）。
- 数据库：
  - 同一 Postgres 实例中包含：
    - `rag_db`：内容/语料库（统一 entries 模型）；
    - （可选）业务库/Schema：工单、通知、档案等事务表。
- 反向代理：
  - Nginx 暴露：
    - `/wecom/webhook` → wechat-backend 回调接口；
    - `/api/...` → 业务接口（如后台管理）。

## 4. 配置与环境变量约定

- 所有敏感信息和环境差异通过环境变量 / [.env](cci:7://file:///d:/AI/.env:0:0-0:0) 管理：
  - 数据库连接：`PG_HOST`, `PG_PORT`, `PG_DB`, `PG_USER`, `PG_PASSWORD`。
  - AI 工厂服务：`AI_FACTORY_BASE_URL` 等。
  - 企业微信：`WECOM_CORP_ID`, `WECOM_AGENT_ID`, `WECOM_SECRET`,
    `WECOM_TOKEN`, `WECOM_ENCODING_AES_KEY` 等。
- 不在代码中硬编码地址/账号/密钥。
- 建议：
  - 本地：使用项目根目录下 `.env.local`（或 `.env.development`）；
  - 服务器：使用环境变量或 `.env.prod`，由运维管理。

## 5. 数据库结构与迁移

- **统一内容库（rag_db）**
  - 保存所有“工作记录 / 笔记 / 对话内容”：
    - 三栏页面记录；
    - 企业微信对话内容；
    - 以及其他通道的工作记录。
  - 区分通道的方式：
    - 字段示例：`source_channel`（`three_column_ui` / `wecom_chat` / ...）
    - 其它关联字段：`project_id`, `workflow_id`, `workflow_node_id`, `department` 等（具体在数据模型文档中定义）。

- **WeCom 消息与对话的统一入库策略（原始素材库视角）**
  - rag_db 当前定位为“原始素材库”，用于统一承载：
    - 三栏页面产生的工作记录；
    - 企业微信中的笔记 / 问答 / 普通聊天记录（按需要接入）；
    - 以及其他通道产生的工作相关内容。
  - 各通道在写入 entries 时，应通过以下元数据区分来源与语义：
    - `extra_context.source_channel`：
      - 示例值：`three_column_ui` / `wecom_dm` / `wecom_group` / `wecom_note_bot` / `wecom_qa_bot` 等；
    - `scene_tags` 中的保留维度：
      - `scene_tags["channel"]`：通道来源（如 `wecom_note_bot` / `wecom_qa_bot` / `wecom_dm` 等）；
      - `scene_tags["semantic_type"]`：语义类型，例如：
        - `"human_chat"`（人与人普通聊天）
        - `"note"`（工作笔记）
        - `"qa_question"` / `"qa_answer"`（问答对）
      - `scene_tags["peer"]`：对话对象摘要，例如：
        - `"wecom:user_zhangsan"` / `"wecom:note_bot"` / `"wecom:qa_bot"`；
      - `scene_tags["conversation"]`：会话 ID，用于将多条消息串联成一段对话视图（如 `conv_wecom_qa_xxx`）。
  - 后续面向 AI 问答 / 知识检索的“高级知识库”和向量库，会在 rag_db 之上基于上述标签进行萃取，
    `entries` 作为统一原始素材仓，不直接承诺是最终形态的“知识库表结构”。

- **迁移原则**
  - 所有表结构变更通过迁移脚本（Alembic / SQL 脚本）执行；
  - 不直接在生产库手工 `ALTER TABLE`；
  - dev / prod 环境的迁移操作须记录在变更日志中。

## 6. WeCom 集成层约定

- WeCom 集成代码应独立为模块（例如 `wecom_gateway`）：
  - 负责：
    - 验证签名；
    - 解密消息体；
    - 将 WeCom 消息转换成内部统一消息结构。
  - 不在这一层写复杂业务逻辑：
    - 入库、调用 AI、工作流推进等逻辑放在 service 层。

- 开发流程建议：
  1. 先实现一个“非加密”的 `/debug/wecom_mock` 接口，用本地工具（Postman 等）模拟消息结构，打通数据流；
  2. 然后再实现真实 `/wecom/webhook` 回调接口，接入企业微信的签名/加解密规则；
  3. 最后再在 dev/测试企业环境中联调真实 WeCom 回调。

### 6.1 企业微信笔记 → entries → 部门工作切片（N1 规则）

- **入口与识别**  
  - wechat-backend 监听企业微信文本消息（单聊/群聊）；  
  - 对以“记：”或等价前缀开头的消息，识别为“工作笔记记录”；  
  - 解析出发送人企业微信 `userid`、消息内容、时间戳、消息 ID 等元数据。  

- **映射到统一 entries_ingest**  
  - wechat-backend 按以下结构调用 ai-factory 的 `entries_ingest` HTTP 接口（伪结构）：  
    - `raw_text`：去掉前缀后的笔记正文；  
    - `user_id`：与企业微信用户一一对应的内部用户 ID（例如 `wecom:{userid}`）；  
    - `note_datetime`：消息发送时间；  
    - `extra_context.source_channel = "wecom"`，并携带企业微信消息/会话相关的元数据。  

- **按部门注入到工作切片**  
  - ai-factory 侧根据 `user_id` 查到用户所属部门 `department_id`；  
  - 根据部门配置，将该条 entries 归入对应部门的“工作切片”视图；  
  - 初始形态下，该记录被视为“没有子卡的普通记录”，尚未被组织为工作/议题/任务/笔记/日程。  

- **执行维度默认落位：其他列**  
  - 在对应部门的工作切片中，这类从企业微信进入的记录：  
    - 不在其他部门或其他工作父卡的工作切片中展示。  
  - 随着后续在 PC 三栏/泳道中的操作（创建子卡、转换为工作/议题/任务/笔记/日程等），其执行维度位置会被重新计算。  

> 该 N1 规则确保：企业微信仅作为“便捷记一笔”的入口，分类与泳道语义全部复用现有 ai-factory / swimlane 体系，不在 wechat-backend 中重复实现业务切片逻辑。

### 6.2 企业微信：聊天 / 笔记 / 问答的元数据约定（素材库层)

> 目标：在不改变 rag_db 作为“原始素材库”的定位前提下,
> 让来自企业微信的不同场景在同一张 `entries` 表中通过元数据被准确区分,
> 为后续的行为分析与知识萃取打基础。

- **统一约定**
  - 所有从 WeCom 进入 AI 工厂的数据，最终都会落到 `entries` 表；
  - 通过以下字段组合区分来源与语义：
    - `project_code` / `user_id`：沿用现有含义；
    - `extra_context.source_channel`：技术通道标记；
    - `scene_tags["channel"]` / `scene_tags["semantic_type"]` / `scene_tags["peer"]` / `scene_tags["conversation"]`：
      - 作为场景标签维度，补充表达“在哪个通道、什么类型、和谁、属于哪段会话”。

- **场景一：工作笔记助手（WeCom Note Bot）**
  - 入口：与“工作笔记助手”机器人会话，或以“记：”前缀开头的消息。
  - 写入 entries 时的推荐约定：
    - `extra_context.source_channel = "wecom_note_bot"`（或 `"wecom"`，视现有约定而定）；
    - `scene_tags["channel"] = ["wecom_note_bot"]`；
    - `scene_tags["semantic_type"] = ["note"]`；
    - `scene_tags["peer"] = ["wecom:note_bot"]`；
    - `scene_tags["conversation"] = ["conv_wecom_note_<消息或会话ID>"]`。
  - 其他部门/执行维度标签仍按 N1 规则通过 `tags_snapshot.department` → `scene_tags.department`、
    `_apply_channel_specific_scene_tags` 等逻辑计算。

- **场景二：AI 问答助手（WeCom QA Bot）**
  - 入口：与“AI 问答助手”机器人会话.
  - 对于**用户问题**：
    - `extra_context.source_channel = "wecom_qa_bot"`；
    - `scene_tags["channel"] = ["wecom_qa_bot"]`；
    - `scene_tags["semantic_type"] = ["qa_question"]`；
    - `scene_tags["peer"] = ["wecom:qa_bot"]`；
    - `scene_tags["conversation"] = ["conv_wecom_qa_<会话ID或msgid>"]`。
  - 对于**AI 回答**：
    - 与对应问题共享相同的 `conversation`；
    - `scene_tags["semantic_type"] = ["qa_answer"]`；
    - 其他标签可按需要补充（如 `status`、`rating` 等）。

- **场景三：人与人普通聊天（可选接入）**
  - 若决定将 WeCom 单聊/群聊也写入 rag_db 作为原始语料，推荐约定：
    - `extra_context.source_channel = "wecom_dm"` 或 `"wecom_group"`；
    - `scene_tags["channel"] = ["wecom_dm"]` / `["wecom_group"]`；
    - `scene_tags["semantic_type"] = ["human_chat"]`；
    - `scene_tags["peer"]`：包含对端用户或群的内部 ID（如 `"wecom:user_lisi"` / `"wecom:chatid_xxx"`）；
    - `scene_tags["conversation"]`：用消息所在 WeCom 会话的唯一标识.
  - 人-人聊天默认不进入“知识/事实库”的向量化流程，只作为行为分析或后续人工筛选的原始素材.

## 7. 广义聊天页面与管理页约定（产品视角）

> 本章约定“员工实际看到的界面形态”，将企业微信原生聊天界面与基于 rag_db 的广义聊天管理页面做角色分工。  
> 原则：对普通员工，优先保证“在聊天里完成 80% 的记与问”；管理页更多面向管理者和运营使用.

### 7.1 企业微信聊天页（原生会话）

- **目标角色**：普通员工（工人）+ 管理者日常使用.
- **入口形态**：
  - 企业微信中至少存在两个机器人/会话入口：
    - 「工作笔记助手」（Note Bot）
    - 「AI 问答助手」（QA Bot）
  - 后续可扩展其他专项机器人.

- **核心功能（首版）**：

  1. **记笔记（Note Bot 会话）**
     - 员工向「工作笔记助手」发送以 `记：` 或同义前缀开头的消息，例如：
       - `记：今天把 X 项目的接口联调完了，还剩 Y 环节需要明天确认.` 
     - wechat-backend 解析消息后，通过 `entries_ingest` 写入 `entries`：
       - `scene_tags.semantic_type = ["note"]`
       - `scene_tags.channel = ["wecom_note_bot"]`
       - `scene_tags.peer` / `scene_tags.conversation` 根据 WeCom `userid` / 会话 ID 填充
       - 其他部门/执行维度标签按 N1 规则计算
     - Bot 返回简要确认文案（可包含时间 + 截断后的内容）.

  2. **问问题（QA Bot 会话）**
     - 员工向「AI 问答助手」以自然语言提问，例如：
       - `我最近一周都干了些什么？`
       - `项目 Y 现在的主要风险点是啥？`
     - wechat-backend 将问题转发至 AI 工厂问答接口：
       - 问题写入 `entries` 作为 `qa_question`
       - AI 回答写入 `entries` 作为 `qa_answer`
       - 问与答共享同一 `scene_tags.conversation`，并标记 `scene_tags.channel = ["wecom_qa_bot"]`
     - Bot 在会话中返回回答文本；必要时附带简单列表（如最近 N 条记录的标题）.

  3. **轻量管理能力（通过问答完成）**
     - 不另起“复杂管理界面”，而是在 QA Bot 会话中支持查询型提问，例如：
       - `列出我最近 10 条笔记`
       - `按时间顺序列一下我上周的工作记录`
       - `把这个月我问过的问题总结一下，按主题分组`
     - wechat-backend + AI 工厂在 rag_db 中检索并由 AI 进行汇总，以“文本 + 简单列表”的形式回复.
     - 这些能力等价于对 rag_db 的“轻管理视图”，但全部通过自然语言交互完成.

- **非目标（首版不在聊天页承载）**
  - 不在企业微信聊天界面内实现复杂的筛选 UI、图表和多维度交叉分析；
  - 团队/部门级的整体视图和可视化分析放在后续的「管理页 / 工作台」中实现.

### 7.2 广义聊天管理页（H5 工作台）

- **目标角色**：管理者、运营、产品/数据分析，以及有意愿“回顾自己工作记录”的员工.
- **入口形态**：
  - 作为企业微信应用内嵌 H5 页面，通过：
    - 企业微信应用菜单（如「工作台」→「广义聊天记录」）
    - 或机器人回复中的链接「在工作台中查看列表」 打开.

- **首版功能范围（最小可用集合）**：

  1. **个人时间线视图**
     - 展示当前登录用户在 rag_db 中的“广义聊天记录”列表，按时间倒序.
     - 列表项可以混排以下语义类型：
       - `note`（笔记）
       - `qa_question` / `qa_answer`（问答对）
       - （可选）`human_chat` 摘要
     - 每条记录显示关键信息：
       - 时间戳
       - 类型图标（笔记 / 问 / 答 / 聊天）
       - 来源通道（如 wecom_note_bot / wecom_qa_bot）
       - 内容前若干字的摘要.

  2. **基础筛选能力**
     - 时间维度：快捷筛选最近 1 / 3 / 7 / 30 天.
     - 类型维度：只看笔记 / 只看问答 / 只看聊天摘要.
     - （可选）简单关键词搜索.

  3. **单条记录操作**
     - 点击记录可查看完整内容和关键信息（含部分 scene_tags）.
     - 支持简单的“星标/关注”操作：
       - 将操作结果映射为 `scene_tags.rating` 或等价标签，写回 `entries`.

- **后续可选演进方向（本阶段不强制实现）**
  - 部门/项目视角的聚合时间线和统计；
  - 话题/标签热度分析（基于 `scene_tags.department/execution/work` 等）；
  - 从记录直接生成/挂接结构化“知识卡片”，进入知识库视图；
  - 管理者对员工使用情况的整体看板（活跃度、覆盖率、改进空间等）.

## 8. 日志与调试约定

- 日志：
  - 统一使用结构化日志（至少包含时间、级别、request_id / trace_id）.
