## 2. 项目背景与目标

### 2.1 业务背景

- **多渠道沟通分散**：企业微信、个人微信、客服系统聊天、语音通话记录、总监/主管笔记等，分散在不同工具和个人设备中，无法形成统一语料、统一视图。  
- **通知触达低效**：重要制度、安全规范、流程变更等，往往需要管理者逐一“人对人”反复沟通，缺乏统一、可监控的点到点通知机制。  
- **知识与经验沉淀不足**：一线问题、投诉、现场事故复盘等大量信息淹没在聊天记录中，没有被结构化为可复用的知识，难以用于培训、预警和优化流程。  

### 2.2 建设目标（总体）

- **目标一：统一通讯与数据采集**  
  - 在企业微信为主的环境下，将与工作相关的聊天、工单沟通、客服记录、通话转写等**统一采集入库**，形成企业级“沟通与行为数据底座”。  

- **目标二：构建通知与执行的闭环**  
  - 支持分级通知、已读/确认/执行情况监控，自动提醒与升级，形成**从发布 → 触达 → 理解 → 执行 → 反馈**的闭环。  

- **目标三：沉淀个人档案与知识库**  
  - 面向员工、外部协作对象构建多维度个人档案；  
  - 将制度、SOP、FAQ、案例等统一管理，形成可检索、可推荐、可追溯来源的知识库。  

- **目标四：对接 AI 工厂，支持智能服务**  
  - 首先落地面向工人的“问一问”机器人；  
  - 逐步将工单辅助、档案画像、风险预警等能力纳入 AI 工厂统一管理的多 Agent 体系。

## 3. 业务范围与边界（v1）

### 3.1 v1 主要范围

- **通讯与会话体系**：工单会话 + 滚动长会话 + 协同小群 + 指挥视角。  
- **多渠道数据采集**：  
  - 企业微信单聊 / 群聊；  
  - 与工作相关的个人微信通道（企业定义）；  
  - 客服系统聊天记录；  
  - 为后续接入通话和笔记预留接口。  
- **通知 / 通告管理与监控**：三类通知分级、评论与可见性、触达与升级机制。  
- **个人档案体系**：覆盖所有员工与关键外部对象，多维度档案与 AI 画像。  
- **知识库结构与知识等级管理**：部门 × 场景双维组织、3+1 知识等级、AI 候选知识池。  
- **AI 应用 v1 场景**：面向工人的“问一问”机器人（嵌入企业微信）。  

### 3.2 暂不纳入 v1 的范围（可作为 v2+ 规划）

- 完整的语音通话自动转写与分析上线（v1 可预留接口，先做小范围 PoC）；  
- 高级 AI 能力：  
  - 工单智能辅助（自动摘要、建议下一步行动）；  
  - 通知/培训助手（自动出题、效果评估）；  
  - 全量风险预警与预测模型。

## 5. 核心业务流程概要

- **流程一：工单派发与沟通**  
  - 指挥/客服基于区域/工人/工单号视图下发工单；  
  - 工人通过工单会话与客服/AI 沟通；  
  - 现场多工人协同时，可建立协同小群；  
  - 所有会话、事件自动挂载到工单与个人档案。  

- **流程二：多渠道信息采集与结构化**  
  - 企业微信/个人微信/客服系统等的聊天数据自动入库；  
  - AI 进行事件识别、情绪/风险标注；  
  - 结构化事件挂载到工单、个人档案、项目、区域等实体上。  

- **流程三：通知 / 通告发布与闭环监控**  
  - 管理者选择通知级别（Ⅰ/Ⅱ/Ⅲ类）、目标人群和阅读/确认要求；  
  - 系统推送并跟踪阅读/确认/测验完成情况；  
  - 未达标人员自动提醒、升级汇报、进入关注名单。  

- **流程四：个人档案的沉淀与使用**  
  - 系统持续从工单、聊天、事件、培训、通知反馈中写入档案；  
  - 员工与管理者查看档案，多视角查看事件时间线、行为标签、AI 画像；  
  - 员工可补充个人说明，管理者可记录点评。  

- **流程五：知识库建设与使用**  
  - 知识管理员从制度文档、聊天/通话、培训材料、复盘中整理知识条目；  
  - AI 自动提炼的内容先进入【候选知识】池，人工审核后升级；  
  - 在工人提问、客服处理工单、AI 回答问题等场景中，系统自动推荐与引用知识。  

- **流程六：AI 问一问机器人使用**  
  - 工人在企业微信中向机器人提问（制度、流程、技术问题等）；  
  - AI 基于知识库 + 历史案例生成回答；  
  - 回答中显式引用知识条目（可点开详情）；  
  - 必要时引导创建新工单或学习任务。

## 6. 功能需求详情

### 6.1 通讯与会话模块

#### 6.1.1 功能目标

- **在企业微信中，为不同角色提供合适的沟通视图：**
  - 工人侧：简单清晰，只看到与自己相关的工单/会话与通知；  
  - 客服/指挥侧：全局/区域视角，像“群聊”一样看到所有工单动态；  
  - 支持多师傅协同与管理议题小群。  

#### 6.1.2 关键功能点

- **工单会话**
  - 每个工单或议题对应独立会话线程；  
  - 会话中可包含文本、图片、语音、文件、位置等内容；  
  - 所有消息自动挂载到工单与相关人员的档案。  

- **滚动长会话（按人）**
  - 每个工人有一条长期的“滚动会话线”；  
  - 用于碎片沟通、临时询问、播报进度；  
  - 作为“个人时间线”由 AI 挖掘潜在事件/工单。  

- **从滚动会话生成工单**
  - **客服人工一键生成**：  
    - 选中若干消息 → “生成新工单会话”；  
    - 系统创建工单实体并建立会话；  
  - **AI 智能提示**：  
    - AI 监控滚动会话，识别潜在“新任务”；  
    - 提醒客服：“是否创建工单？”  

- **协同小群**
  - 支持邀请多名工人、客服、管理者加入；  
  - 可挂靠：某个工单 / 项目 / 区域 / 管理议题；  
  - 人工或 AI 均可发起建群；  
  - 群内重要片段可提炼为事件/知识，挂到相应对象上。  

- **指挥/客服视图**
  - 按【区域 → 工人 → 工单】三级导航；  
  - 显示每个工人当前工单列表与最近动态；  
  - 可筛选：按状态、按风险标签、按投诉情况等。  

- **可见性规则**
  - 工人：只见自己相关的工单/滚动会话、自己与 AI 对话；  
  - 客服：可见全部或负责范围内的工单与会话；  
  - 管理层：可按权限查看跨区域/跨部门的视图。

### 6.2 多渠道信息采集模块

#### 6.2.1 功能目标

- 将所有与工作相关的关键沟通来源最大化地统一采集，形成企业数据底座，为档案、知识库、AI 分析提供原料。

#### 6.2.2 v1 接入范围

- **企业微信单聊 / 群聊**（核心渠道，默认视为工作相关，无隐私）；  
- **个人微信中与工作相关的通道**（按企业策略识别与限定）；  
- **客服系统聊天记录**；  
- 预留语音通话转写与总监/主管笔记的导入接口.

#### 6.2.3 数据处理要求

- **完整原文 + 元数据存储**  
- **AI 事件识别**：投诉、请假、报销申请、违章上报、紧急事件等；  
- **情绪 / 风险标签**：愤怒、焦虑、中立，及潜在流失、潜在事故等风险标志；  
- **挂载规则**：  
  - 有工单号 → 挂工单；  
  - 无工单号但关系到某人 → 挂个人档案原始素材；  
  - 适合抽象为通用知识 → 进入知识候选池或公共知识库.

#### 6.2.4 信息库与内容统一入库原则

- 本系统中所有与“工作记录 / 笔记 / 对话内容”相关的信息（包括但不限于）：  
  - 三栏页面中产生的计划、笔记、工作记录；  
  - 通过企业微信产生的对话内容（工人 ↔ 客服、工人 ↔ AI 助手等）；  
  - 后续接入的客服日志、通话转写、总监/主管的工作记录等；  
  **都视为同一类“工作语料”，统一进入 ai-factory 使用的内容库 `rag_db`。**  

- 统一入库的目标：  
  - 在一个库内形成完整的“时间线 + 语料”视图，支持：  
    - 统一的 RAG 与问答（不区分来自三栏页面还是企业微信等通道）；  
    - 统一的统计分析与画像（可以按来源、角色、项目等维度切片）；  
    - 更简洁的知识沉淀与复用链路.  

- 在 `rag_db` 内，通过字段区分不同来源通道，例如：  
  - `source_channel`：`three_column_ui` / `wecom_chat` / `customer_service_log` / `phone_call` 等；  
  - `source_app`：`swimlane` / `wechat_bot` 等；  
  - `origin_id`：外部消息 ID（如企业微信 message_id / 会话 id）。  

- 已实现的三栏页面只是众多“入库通道”中的一个；企业微信对话采集通道将与之并列：  
  - 三栏页面通道：将用户在前端三栏中形成的记录写入 `rag_db`；  
  - 企业微信通道：将企业微信中的对话内容经过清洗/结构化后，同样写入 `rag_db` 的工作记录/笔记结构，并带上来源标记。  

> 设计原则：**内容统一入一个信息库（rag_db），通道用字段区分；业务事务表（工单、通知、档案基础信息等）可以在同一 Postgres 实例中按库/Schema 单独管理。**

#### 6.2.5 企业微信笔记录入与部门工作切片对齐（N1）

- **统一笔记语义**  
  - 企业微信中通过“记：……”或等价入口产生的内容，视为与三栏页面“笔记通道”相同的工作记录/笔记。  
  - 入库后统一写入 `rag_db.entries`，复用同一套检索、档案和知识沉淀链路。  

- **按部门映射到工作切片**  
  - 每个用户在企业微信侧有唯一所属部门（或主部门）；  
  - 系统根据用户所属部门，将其在企业微信中记下的笔记，自动归入对应部门的“工作切片”视图；  
  - 不同部门的笔记不会混入同一个工作切片。  

- **默认落位：执行维度的“其他”栏**  
  - 对于从企业微信进入系统的笔记：  
    - 初始视角下，统一视为“尚未被组织为工作/议题/任务/笔记/日程的单条记录”；  
    - 在对应部门的工作切片中，默认显示在执行维度的“其他”列；  
    - “其他”列仅表示“没有子卡、尚未结构化的记录”，而非“无关紧要”。  

- **后续演化由三栏/泳道完成**  
  - 部门负责人或相关人员可以在 PC 三栏/泳道界面中：  
    - 将这些来自企业微信的记录加工为工作/议题/任务/笔记/日程等；  
    - 为其新增子卡、建立父子关系；  
  - 一旦记录被结构化，其在执行维度中的位置将随之变化，不再停留在“其他”列，而是进入相应的工作家族结构。  

> 通过上述约定，企业微信通道仅作为“便捷记一笔”的入口；笔记一旦入库，即完全融入现有的三栏/泳道体系，由部门工作切片统一承载和展示。

### 6.3 通知 / 通告模块

#### 6.3.1 通知类型

- **Ⅰ类（强制必读 + 时限确认）**：安全、制度红线等；  
- **Ⅱ类（重要通知 + 建议阅读）**：流程调整、工作重点安排等；  
- **Ⅲ类（一般信息 / 学习资料）**：分享、培训内容、案例等。  

#### 6.3.2 功能点

- **发布配置**
  - 选择通知类型、目标人群、阅读/确认要求、截止时间；  
  - 配置评论是否开放、评论可见范围。  

- **阅读与行为监控**
  - 已读率、时限内阅读率；  
  - 是否点击“确认已理解”；  
  - 是否完成相关测验/问答；  
  - 后续行为是否改善（与违章/投诉/事故等数据对齐分析）。  

- **自动补救机制**
  - 未读/未确认人员自动多次提醒（节奏可配置）；  
  - 升级通知给直接上级（小组长/总监）；  
  - 将持续未达标人员加入“关注名单”，作为培训与管理决策参考。  

- **评论与互动**
  - 通知可开启评论区；  
  - 支持员工设置“我的评论是否对他人可见”；  
  - 管理者可按通知查看评论舆情与反馈主题。

### 6.4 个人档案模块

#### 6.4.1 覆盖对象

- **公司内部员工**：所有岗位；  
- **外部关键主体**：客户、甲方、协作单位员工、招聘候选人等。  

#### 6.4.2 档案内容

- **基础信息**：身份/合同、岗位、技能等级、证照、所属区域/班组等。  
- **工单与绩效**：工单数量、时效、返工率、投诉/表扬统计。  
- **行为与习惯标签**：准时性、配合度、安全规范遵守、响应速度等。  
- **事件时间线**：按时间列出正向/负向/重大事件。  
- **学习与培训记录**：参与培训、考试结果、错题分布、学习轨迹。  
- **AI 画像与视图**：  
  - 本月表现画像；  
  - 危险与风险提示；  
  - 建议辅导方向、适合岗位/成长路径。  

- **多视角画像模板**
  - 系统支持按不同维度生成和保存“画像模板”，如：  
    - 安全风险画像；  
    - 客户满意度画像；  
    - 学习投入画像；  
    - 管理潜力画像。  

#### 6.4.3 可见性与员工反馈

- **员工可见内容**

### 6.5 知识库模块

#### 6.5.1 组织结构

- **双维度组织：部门 × 场景**
  - 部门：现场、客服、内务、总部、软件等；  
  - 场景/任务：接单、到场、施工、验收、回访、请假、报销、安全培训、投诉处理等；

#### 6.5.2 知识条目来源

- 正式制度文档与 SOP；  
- 聊天 / 通告 / 通话中提炼的 FAQ；  
- 培训课件、总监笔记与复盘报告；  
- 一线经验分享与典型案例。

#### 6.5.3 知识等级（3+1）

- 【正式标准】  
- 【操作指引】  
- 【经验分享】  
- 【候选知识】（AI/系统自动提炼，尚未人工审核）  

#### 6.5.4 AI 候选知识审核流程（X 方案）

- AI 将高价值片段提炼为候选知识条目；  
- 候选知识进入“仅知识管理员可见”的池；  
- 知识管理员可进行：  
  - 审核通过并定级为正式标准/操作指引/经验分享；  
  - 退回/删除/合并；  
- 审核通过前，普通员工不可直接在知识库中检索到候选条目。  

#### 6.5.5 知识使用场景（v1 优先）

- 工人提问时的自动推荐；  
- 客服处理工单时的解决方案推荐；  
- AI 回答问题时显式引用知识条目（含链接）。

### 6.7 权限与数据可见性管理

> **v1.2 重要补充**：基于企业微信部门架构的权限管理设计

#### 6.7.1 权限模型总体设计

**四层权限隔离机制**：

| 隔离层级 | 字段标识 | 作用范围 | 实现方式 |
|---------|---------|---------|----------|
| **L1: 用户隔离** | `user_id` | 用户只能访问自己的数据 | RLS + 应用层过滤 |
| **L2: Agent类型隔离** | `agent_type` | 笔记助手 vs 问答助手数据隔离 | 应用层过滤 |
| **L3: 部门实例隔离** | `agent_instance_id` | 不同部门的助手数据隔离 | RLS + 应用层过滤 |
| **L4: 会话隔离** | `session_id` | 同一用户不同会话数据可区分 | 应用层过滤 |

**关键特性**：
- ✅ **数据库层保障**：PostgreSQL RLS（Row Level Security）强制隔离
- ✅ **应用层保障**：contextvars + 显式过滤双重保障
- ✅ **部门层级支持**：支持父子部门的权限继承

#### 6.7.2 基于部门的数据可见性规则

**规则1: 默认部门隔离**

```
场景：张三（技术部）查看工作笔记
规则：只能看到技术部的笔记
实现：scene_tags.department = [1]  // 1=技术部
```

**规则2: 包含子部门**

```
场景：技术总监查看技术部所有笔记
规则：可以看到技术部 + 研发组 + 测试组的笔记
实现：
  - get_department_users(dept_id=1, include_children=True)
  - 返回所有子部门的数据
```

**规则3: 跨部门授权**

```
场景：项目经理查看跨部门项目信息
规则：通过项目标签授权，可查看多个部门的相关数据
实现：scene_tags.project = ['project_X']
```

**规则4: 部门负责人特权**

```
场景：部门leader查看下属工作记录
判断：is_department_leader(userid, dept_id) = True
权限：
  - 可查看本部门所有成员的笔记
  - 可查看本部门的统计分析
  - 可管理本部门的知识库
```

#### 6.7.3 权限检查实现方式

**方式1: 数据库层面（RLS策略）**

```sql
-- PostgreSQL行级安全策略
CREATE POLICY user_agent_isolation ON entries
    FOR ALL
    USING (
        user_id = current_setting('app.current_user_id', true) OR
        current_setting('app.current_user_id', true) IS NULL
    );

-- 设置上下文
SET app.current_user_id = 'wecom:zhangsan';
SET app.current_agent_type = 'wecom_note_bot';
SET app.current_agent_instance_id = 'dept_001_note';

-- 查询自动过滤，只返回允许的数据
SELECT * FROM entries;  -- 自动只返回zhangsan有权限的数据
```

**方式2: 应用层面（Scene Tags过滤）**

```python
# 搜索时的权限过滤
def search_with_permission(user_id: str, query: str):
    # 1. 获取用户所属部门
    user_info = wecom_org.get_user_detail(user_id)
    user_depts = user_info.get("department", [])
    
    # 2. 构造部门过滤条件
    filters = {
        "scene_tags.department": user_depts  # 只搜索用户所在部门的数据
    }
    
    # 3. 如果是部门负责人，可以包含子部门
    if is_department_leader(user_id, user_depts[0]):
        child_depts = get_child_departments(user_depts[0])
        filters["scene_tags.department"] = user_depts + child_depts
    
    # 4. 调用搜索接口
    return memory_client.search_entries(
        query=query,
        user_id=f"wecom:{user_id}",
        agent_type="wecom_note_bot",
        filters=filters
    )
```

#### 6.7.7 权限管理最佳实践

**原则1: 最小权限原则**
- 默认只授予必要的访问权限
- 需要更多权限时通过审批流程

**原则2: 部门优先原则**
- 优先使用部门架构进行权限管理
- 减少个人级别的特殊授权

**原则3: 显式授权原则**
- 跨部门访问需要明确授权
- 通过项目标签、角色标签授权

**原则4: 可追溯原则**
- 所有权限变更都有审计日志
- 重要操作需要留痕
