# 表结构设计（初稿）

> 更新日期：2025-12-08
> 说明：本文件汇总当前关于“流水主表 + 空间标记 + 解释层快照”的整体表结构设计，后续可持续增补。

---

## 1. 分层思路：事实层 vs 解释层

### 1.1 事实层（Fact Layer）

- 职责：保存**真实发生的记录**（笔记、任务、议题、工作流中的每一条事件）。
- 特点：
  - 所有记录都是“流水记录”。
  - 统一的基础结构：标题 + 内容 + 创建时间 + 若干 6W（who/when/where/what/why/how）要素。
  - 作为 RAG 的**唯一真实来源**。

### 1.2 解释层（Interpretation Layer）

- 职责：保存**对事实层的结构化理解**，例如：
  - 全局战略地图
  - 某个项目/节点的局部脑图
  - 难点拆解视图
- 特点：
  - 来自 Agent + RAG 的“推导结果”。
  - 可以随时重算；
  - 只有少量“里程碑/关键节点/难点视图”需要长期保存。

---

## 2. 事实层：流水主表设计（entries）

> 目标：尽量简化，在一张表里承载所有类型的记录，通过少量字段形成“树形结构 + 空间标记”。

### 2.1 核心字段

建议的基础字段（名称可与现有 `raw_entries` 对齐）：

- **`entry_id`** (`text`, PK)
  - 流水记录的唯一 ID。

- **`title`** (`text`)
  - 标题。

- **`content`** (`text`)
  - 正文内容（Markdown / 纯文本）。

- **`created_at`** (`timestamptz`)
  - 记录创建时间（入库时间）。

- **`note_datetime`** (`timestamptz`, 可选)
  - 业务时间（例如事件实际发生时间），便于按“业务时间线”排序。

- **6W 相关字段**（可以拆分，也可以统一放在 JSON 中）：
  - `who` / `where` / `what` / `why` / `how` 等，
  - 或 `sixw_json` (`jsonb`)：用结构化方式存储 6W。

- **项目/上下文相关**（可沿用现有字段）：
  - `project_code` (`text`)：项目/工作流代码。
  - `project_hint` (`text`)：面向人的项目提示名。

- **状态与附加元数据**：
  - `status` (`text`)：active / archived 等。
  - `extra_meta` (`jsonb`)：附加元数据（前期可空，后期按需扩展）。

- **场景标签（支持三栏/五栏查询）**：
  - `scene_tags` (`jsonb`, 可空)：用于存储“部门/规划/执行/公共/状态/评价”六行场景标签，结构示例：

    ```jsonc
    {
      "department": ["总部"],
      "planning": ["目标"],
      "execution": ["项目"],
      "common": ["笔记"],
      "status": ["交付"],
      "rating": ["节点", "关注"]
    }
    ```

  - 该字段主要作为 `ai_factory.db.nodes_repo` 与 `ai_factory.query.NodeQuery` 的物理承载，用于按场景标签过滤节点列表。

### 2.2 树形结构与“空间标记”字段

#### 2.2.1 标签语义层 vs 父子关系物理层（含创建/移动/复制继承）

- **语义层（标签层）**
  - 通过标签体系表达“父子关系的语义结构”，例如：
    - 三栏/五栏中的「部门 → 规划 → 执行」顺序标签；
    - `space_type ∈ {goal,strategy,plan,project,task,topic,note}` 表达“这一条记录在空间中的角色/层级”。
  - 标签决定：
    - 节点的**角色/层级类型**（space_type、三栏场景标签等）；
    - **允许的上下级组合关系**（哪些类型可以挂在哪些类型下面，例如 task 可以挂在 project 下，note 可以挂在 task/topic 下）。

- **物理层（ID 层）**
  - 通过 `entry_id / parent_entry_id`（或后续若引入的关系表 `parent_entry_id / child_entry_id`）表达**具体节点之间的父子边**：
    - “我挂在谁下面”只看 ID 对，不靠标签临时推断；
    - 如果将来允许多父、多视角，也由多条 ID 边精确表达。
  - 所有树形视图（脑图 UI、泳道/永道、三栏树等）在渲染和查询阶段，**一律以 ID 对为最终事实来源**。

- **语义层 → 物理层：由语义规则驱动物理结构更新**

  - **创建新节点（Create）**
    - 在某个父节点下新建节点时：
      1. 语义层根据当前父节点的标签与场景语义，自动为新节点生成初始标签集（如继承部门/规划/执行/项目代码等，可按产品策略配置哪些标签“必继承”、哪些“可继承/需重选”）。
      2. 物理层生成新的 `entry_id`，并写入 `parent_entry_id = 父节点的 entry_id`，形成一条新的父子边。
    - 换句话说：**新节点的物理父子关系由当时的标签语义 + 用户操作共同决定**。

  - **移动节点（Move）**
    - 当用户把某个节点从原父节点拖动到新的父节点下时：
      1. 语义层先根据新父节点的标签和结构规则，对该节点的标签做合法性校验与必要修正（例如不允许某种 space_type 挂在不合法父节点下；或要求随父节点更新部门/规划等场景标签）。
      2. 物理层更新该节点记录中的 `parent_entry_id = 新父节点 entry_id`，从而在结构上完成父子关系的重连。
    - UI 展示与后续查询都以更新后的 ID 对为准，标签仅作为类型/过滤信息存在.

  - **复制节点（Copy/Duplicate）**
    - 当复制某个节点到新的父节点下时：
      1. 语义层通常完整继承源节点的标签集（也可以根据新父节点语义做附加修正，例如继承部门/规划但清空状态/评价标签）。
      2. 物理层为副本生成新的 `entry_id`，并设置 `parent_entry_id = 目标父节点 entry_id`，形成一条新的父子边；源节点的 ID 及父子关系保持不变。
    - 这样，复制操作在语义上“继承原节点含义”，在物理结构上“新增一条平行分支”。

  - **规划链条与执行节点的父子关系（v0 语义约定）**
    - 规划链条采用一条自上而下的严格父子路径：
      - `strategy`（战略） → `goal`（目标） → `plan`（计划） → `project`/`workflow`（项目/工作流）。
      - 其中每一层都是下一层的“自然父节点”，默认不允许在该链条上随意跳级挂载（例如 `project` 不直接挂在 `strategy` 之下），除非后续产品策略显式放宽。
    - 执行节点包括四类：`task`（任务）、`topic`（议题）、`note`（笔记）、`schedule`（日程）。
      - 这四类在语义上处于同一“执行层”，彼此之间是平级关系，不预设谁必须是谁的父节点。
      - 它们可以作为**规划链条上任意一个节点**的子节点，即：`strategy`/`goal`/`plan`/`project` 任一层下，都可以挂载 `task`/`topic`/`note`/`schedule`.
      - 同时，这四类执行节点之间**允许自由嵌套**：任意一个执行节点都可以作为另一条执行节点的父节点，例如任务下挂任务/议题/笔记/日程、议题下挂任务/笔记等，不做硬性限制.
    - 在实现上：
      - 规划链条的严格父子关系主要体现在 `space_type ∈ {strategy, goal, plan, project}` 之间的组合约束上；
      - 执行节点的自由嵌套体现在允许 `parent_entry_id` 指向任意一个规划/执行节点，只由上层业务规则决定是否提示或校验.
      - UI 在创建/移动节点时，应先根据当前父节点的 `space_type` 与上述语义约定进行合法性判断，再写入/更新 `parent_entry_id`.

- **设计原则小结**
  - 标签层是**语义层**：定义节点类型、层级、允许的上下级组合，以及创建/移动/复制时的继承策略；
  - `entry_id / parent_entry_id` 是**物理层**：唯一承载“谁是我的父亲”的结构事实；
  - 在实现上，**由语义层（标签 + 用户操作意图）驱动物理层（ID 对）的生成与更新**，查询与渲染阶段一律以物理层为准，语义层用于过滤、显示和结构合法性校验.



> 通过极少数字段，在同一张表中表达目标/战略/计划/项目/任务/议题/笔记的大树结构.

- **`space_type`** (`text`)
  - 用于表达“这条记录在空间中的角色/层级”：
  - 取值枚举（初版）：
    - `goal`     —— 目标（Goal）
    - `strategy` —— 战略（Strategy）
    - `plan`     —— 计划（Plan）
    - `project`  —— 项目 / 工作流（Project / Workflow）
    - `task`     —— 任务（Task）
    - `topic`    —— 议题（Topic / Issue）
    - `note`     —— 笔记（Note）
  - 允许为空（`NULL`）：表示尚未归类，或纯流水记录。

- **`parent_entry_id`** (`text`, FK→`entries.entry_id`, 可空)
  - 指向同表中的另一条 `entry_id`，表示“**我挂在谁下面**”：
    - 某个 `task` 的 `parent_entry_id` 可以指向一个 `project`；
    - 某个 `note` 的 `parent_entry_id` 可以指向一个 `task` 或 `topic`。
  - 通过这一字段，在单表内形成树形结构：

    ```text
    entry_id (goal)
      └─ entry_id (strategy)
          └─ entry_id (plan)
              └─ entry_id (project)
                  └─ entry_id (task)
                      └─ entry_id (topic)
                          └─ entry_id (note)
    ```

### 2.3 其他可保留字段（与现有 raw_entries 兼容）

- `section_id`：用于表达“同一会话/小节/局部段落”的分组键。
- `question` / `answer`：对问答型记录保留结构化支持。
- `raw_markdown` / `refined_block_text`：原始文本与精炼块文本。
- `auto_title` / `short_summary`：自动标题与简要摘要。

> 这些字段可以继续存在于事实层，但在“轻量视图”中不一定全部暴露。

### 2.4 一张流水主表 + 两个字段就够了（大树 & 空间标记一体化）

在以上设计下，可以把事实层的核心思想总结为：

- **一张流水主表承载所有记录**：
  - 所有笔记、任务、议题、项目、目标等，统一存放在 `entries` 一张表中；
  - 关键字段包括：`entry_id`, `title`, `content`, `created_at`，若干 6W 要素（或 `sixw_json`），以及 `project_code`, `status`, `extra_meta` 等。

- **两个关键字段完成“空间标记 + 树形结构”**：
  - `space_type` 决定“这一条记录在空间中的角色/层级”（goal/strategy/plan/project/task/topic/note）；
  - `parent_entry_id` 决定“这一条记录挂在哪个上级节点下面”（指向同表中的另一条 `entries.entry_id`）。

只依靠这一张表 + 这两个字段，就可以自然表达出所需的“大树”结构：

- 是否形成大树：
  - 是的，所有节点都是 `entries` 中的记录，父子关系通过 `parent_entry_id` 串起来；
- 是否以空间标记驱动结构：
  - 是的，`space_type` 决定该节点是目标 / 战略 / 计划 / 项目 / 任务 / 议题 / 笔记中的哪一类.

典型查询示例（伪代码）：

- 某个项目下的所有任务：

  ```sql
  SELECT *
  FROM entries
  WHERE space_type = 'task'
    AND parent_entry_id = '<某个 project 的 entry_id>';
  ```

- 某个任务下的所有笔记：

  ```sql
  SELECT *
  FROM entries
  WHERE space_type = 'note'
    AND parent_entry_id = '<某个 task 的 entry_id>';
  ```

### 2.5 与向量库 metadata、静态/动态标签的关系（设计说明）

> 本小节只做“字段用途与约定”的说明，不额外引入新的物理字段.

1. **事实层 → 向量库的基本映射**
   - 对 `entries` 中的记录做向量化（embedding）时，建议在向量库中至少保留：
     - `entry_id` 或 `section_id`：作为与事实层 join 的主键；
     - 关键标签：可以从 `scene_tags` 中抽取少量维度（如 department/planning/execution/status）写入向量库的 `metadata`，用于过滤与分桶；
     - 适量的 `extra_meta` 字段：如 `project_code`、业务时间等，按实际需要选择.

2. **静态标签：当前阶段的主要标注方式**
   - 现阶段，场景标签（`scene_tags.department/planning/execution/status/...`）和 `space_type`/`parent_entry_id` 是**静态、可控的结构化标注**：
     - 在向量库中，可以直接作为 metadata 字段参与过滤（如按部门/层级/执行类型/状态筛选）；
     - 也可以在需要时拼入待编码文本中，增强语义聚焦度（例如在向量文本前面附加“【部门=软件】【规划=计划】”）。

3. **动态标签：作为未来扩展的语义信号**
   - 随着 AI 标注与关系图谱的引入，会产生一批**动态标签**，例如：
     - 使用频率高/近期高频；
     - 风险高/异常多；
     - 主题聚类结果、相似项目族等.
   - 这类标签不适合立即固化为强 schema 字段，建议统一存放在：
     - `entries.extra_meta`（如 `extra_meta.ai_tags` / `extra_meta.graph_labels`）；
     - 向量库记录的 `metadata.ai_tags` / `metadata.graph_labels` 等键中.
   - 在向量检索视角下，可以将动态标签视为：
     - 类似于自动标题/summary 的“额外语义维度”；
     - 既可参与文本编码（拼入待编码文本），也可作为 metadata 维度用于过滤/重排，提高召回的相关性与效率.

4. **设计原则小结**
   - 结构型字段（`entry_id` / `space_type` / `parent_entry_id` / `scene_tags` 基本结构）尽量稳定、统一，作为“骨架”；
   - 静态标签（部门/规划/执行/状态）作为当前阶段的主要标注手段，既服务三栏/永道等视图，也服务向量检索；
   - 动态标签与 AI 标注遵循“meta 扩展”策略：不破坏骨干结构，只在 `extra_meta` 与向量库 metadata 中增减键值即可.

### 2.5 与 RAG / 脑图 UI 的关系（开发者视角小结）

- **RAG 视角**：
  - 从 `entries` 中提取 `title + content + created_at` 以及 `space_type`, `project_code`, `parent_entry_id` 等元数据；
  - 进行切分和 embedding，写入向量相关表；
  - 检索时只操作 chunk/embedding 表，命中后通过 `entry_id` 回到同一张流水主表。

- **脑图 UI 视角**：
  - 直接基于 `entries` 的 `entry_id / parent_entry_id / space_type / title` 渲染树形结构或局部子树；
  - 不需要另外维护一套“脑图专用表”，只是对同一套数据做不同视图的呈现。

一句话总结：

- **一张流水主表（entries） + `space_type` + `parent_entry_id`**，就足以同时支撑“大树结构 + RAG 检索 + 脑图 UI 三种视角”，后续扩展只需在此基础上继续演进。

## 3. RAG 与向量检索

事实层的 `title + content + created_at + meta(space_type, project_code, parent_entry_id 等)`
可作为 RAG 的索引源：

- 由切分/embedding 逻辑生成 **chunk 表** 与 **embedding 向量表**（例如：
  - `entry_chunks(chunk_id, entry_id, chunk_index, chunk_text, meta_json)`
  - `entry_chunk_embeddings(chunk_id, embedding vector, meta_json)`
- 向量检索只操作 chunk/embedding 表，命中后通过 `entry_id` 回到主表。

> 目前仅做思路记录，具体表结构可在后续 RAG 设计阶段详化。

## 4. 解释层：地图/脑图快照表设计

> 解释层用于保存“对当前事实的结构化理解”，如战略地图、局部项目脑图、难点拆解图等。

### 4.1 快照表 `map_snapshots`（草案）

```sql
CREATE TABLE map_snapshots (
    map_id         text PRIMARY KEY,        -- 快照 ID（uuid）
    scope          text NOT NULL,           -- 作用范围，如 'global', 'project:XYZ', 'node:ENTRY_ID'
    map_type       text NOT NULL,           -- 图类型：'strategic', 'local', 'issue_overview' 等
    importance_tag text NOT NULL,           -- 保存级别：'milestone' / 'node' / 'difficulty' / 'ephemeral'
    created_at     timestamptz NOT NULL DEFAULT now(),
    created_by     text,                    -- 谁触发（user / agent）
    source_filter  jsonb NOT NULL,          -- 本次生成依据的过滤条件（时间范围、project_code 等）
    source_ids     jsonb NOT NULL,          -- 参与生成的 entry_id 列表或聚合条件
    graph_payload  jsonb NOT NULL           -- 实际脑图结构（nodes/edges/attributes）
);
```

### 4.2 `importance_tag` 语义

- `milestone` —— 里程碑版本
  - 必须保存，长期保留或按较长周期清理；
- `node` —— 关键节点结构
  - 某个节点/子树的重要阶段性结构，可只保留最近 N 版；
- `difficulty` —— 难点/卡点视图
  - 用于跟踪问题的形成、拆解与解决，可按需保留；
- `ephemeral` —— 实时浏览
  - 一般不落库；若落库也可按规则定期清理.

> 建议：**实时浏览默认不写入 `map_snapshots`**，只有当用户或 Agent 明确标记为“需要保存”时，才以合适的 `importance_tag` 写入.

### 4.3 “印象节点 / 解释视图”与 `entries` 的关系

- 解释层中的每一条 `map_snapshots` 记录，可以视为一个“印象节点 / 印象树快照”（impression）：
  - `graph_payload` 承载某一时刻、某一视角下的结构化认知（战略图、项目局部图、难点拆解图等）；
  - `source_ids` 以列表形式记录本次印象所依据的 `entries.entry_id` 集合，是**从印象回溯事实层的唯一入口**；
  - `scope/map_type/importance_tag` 用于表达“从哪个角度看、这是一类什么视图、需要保留多久”。

- 设计原则：
  - **事实只进入 `entries`，印象只进入 `map_snapshots`**：
    - 日常由 Agent 生成的各种关系图、印象树，只要属于“对现有事实的理解”，都落在 `map_snapshots`；
    - 不直接在 `entries` 中新增 `is_impression` 等字段，以免事实层被大量短期视图污染.
  - **仅少量“固化后的印象”回写事实层**：
    - 当某个印象树已上升为长期有效的结论/结构（例如正式的战略地图、通过评审的项目结构），
      可以通过迁移脚本将其固化为新的 `entries` 记录（如 `space_type = 'map'`），
      同时在 `map_snapshots` 中用额外字段（如 `final_entry_id`）指向对应的事实节点.
  - **生命周期与清理策略在解释层完成**：
    - 结合 `importance_tag` 和时间（如 `created_at/updated_at`），
      可在 `map_snapshots` 上周期性执行清理任务：
      - `ephemeral` 视图仅保留最近一段时间；
      - `node/difficulty` 视图可以只保留最近 N 个版本；
      - `milestone` 视图长期保留或极少清理.

> 小结：事实层 `entries` 承载“真的发生了什么”，解释层 `map_snapshots` 承载“我们如何在某一刻理解这些事实”.
> 印象可以大量、频繁地生成，但只需将少量重要版本固化并回写为新的事实节点，其余则通过解释层的生命周期策略控制存留时间.

---

## 5. 使用与演进建议

1. **事实层先稳住**：
   - 以现有 `raw_entries` 为基础，逐步向“流水主表 + space_type + parent_entry_id”演进；
   - 不急于大规模拆表，只要核心字段语义清晰即可.

2. **解释层先走轻量快照路线**：
   - 使用一张 `map_snapshots` 表记录少量**重要**的地图版本；
   - 大多数“当前视图”通过 RAG + Agent 实时计算，不做持久化。

3. **与脑图前端的接口设计**：
   - 实时视图：RAG + Agent → in-memory graph → 脑图组件；
   - 历史视图：查询 `map_snapshots`，根据 `graph_payload` 直接还原脑图。

4. **后续扩展**：
   - 若未来需要更细粒度的图数据库能力（路径计算、大规模图算法），可再考虑引入 Neo4j/图数据库，并将 `graph_payload` 或节点/边迁移过去；
   - 当前阶段以 PostgreSQL + pgvector + JSONB 即可支撑研发与中期规模。

## 7. 场景标签（scene_tags）与通用查询

> 目标：为三栏/五栏等前端提供一个统一的“场景标签查询”物理承载。

1. **字段位置与结构**
   - 在 `entries` 上新增 `scene_tags jsonb` 字段，结构固定为六个 key：

     ```jsonc
     {
       "department": ["总部"],
       "planning": ["目标"],
       "execution": ["项目"],
       "common": ["笔记"],
       "status": ["交付"],
       "rating": ["节点", "关注"]
     }
     ```

   - 六行的取值集合由前端按钮固定控制，不在 DB 中动态扩展。

2. **写库侧约定**
   - 三栏/五栏写入 `entries` 时：
     - 根据 UI 中当前选中的“部门/规划/执行/公共/状态/评价”按钮，构造上述 `scene_tags` 结构；
     - 未选中的行写空数组 `[]` 或整个字段置为 `NULL`（由集成层统一约定）。

3. **查询侧的使用方式**
   - `ai_factory.query.NodeQuery` / `SceneTags` 负责描述查询条件；
   - `ai_factory.db.nodes_repo.NodeDBFilters.tags` 将上层标签映射为 `scene_tags` 上的过滤条件：
     - 每个非空标签行会生成一条 `(scene_tags->'key') ?| ARRAY[...]` 的 SQL 片段；
   - `query_nodes_basic` 按标签 + 时间窗口 + 分页返回节点列表；
   - `query_nodes_hot` 在此基础上结合 `time_window_days` 与 `created_at` 计算简单的 `activity_score`，用于“热节点列表”视图。

> 通过这一设计，场景标签的写入与查询都落在 `entries.scene_tags` 一处，既方便三栏/五栏前端固化按钮组，也便于 AI 工厂在 DB 层做统一优化与索引。


## 6. 流水输入与 Agent 自动切块写库流程

> 目标：在**输入侧保持完全自由**（用户可一次粘贴多轮会话），在**写库侧保证结构干净**（entries 表中的记录是语义自然块），通过 Agent 作为中间层实现。

### 6.1 流程概览

1. **用户输入流水**
   - 不对输入内容做硬性约束：
     - 可以是一句、一段、一次会话；
     - 也允许一次粘贴多轮会话/大段历史记录。

2. **写库前调用 Agent 做“语义切块”**
   - Agent 对整条输入进行分析：
     - 根据语义、结构、长度等因素，将原始输入拆分为 `块1, 块2, ..., 块N`；
     - 对每个块生成：
       - `title_ai`：规范化标题；
       - `summary_ai`：概括性摘要（通常 3–6 句，信息密度高）；
       - `structured_json`：结构化要素（6W、标签、space_type 建议值等）。

3. **按“块”为单位写入事实层 entries 表**
   - 为每个块生成新的 `entry_id`，以自然块为粒度写库：
     - `entry_id`：该块的主键；
     - `content` / `content_raw`：块文本；
     - `title_ai` / `summary_ai` / `structured_json`：Agent 生成的解释信息；
     - 其他字段（`project_code`、`space_type` 建议值等）按需要填充。
   - 可选地，为了追踪“本次输入拆出的所有块”，增加：
     - `source_batch_id`：同一次原始输入的批次 ID（uuid）。

4. **（可选）原始整条输入的保留方式**
   - 若需要保留“原始大段粘贴内容”以便审计/回溯，可单独存入：
     - 日志表 `raw_input_log(batch_id, raw_text, created_at, created_by, meta_json)`；
     - 或文件/日志系统中，不直接进入 entries 主表。

### 6.2 Agent 切块策略要点

- **不在用户侧强行规定“一个流水 = 一个自然块”**，但在设计规范中推荐这一习惯；
- Agent 在写库前负责：
  - 检查长度：过短的句子可合并，过长文本应拆分；
  - 检测明显的多会话结构（如多段时间戳、分隔符等）；
  - 在保证语义完整的前提下进行切分，避免在一句话中间截断。

### 6.3 与向量检索的关系

- entries 表中的每一条记录，即一个 **自然语义块**；
- 对每个块：
  - 使用 `title_ai + summary_ai` 作为主要的向量化输入；
  - 必要时再对 `content` 做更细粒度的 chunk 以支持精细 RAG；
- RAG 在召回时：
  - 先基于向量（`title_ai + summary_ai`）做粗召回；
  - 再根据 `space_type`、`project_code`、`structured_json` 中的标签做过滤或重排序；
  - 命中后为人/模型展示时，可同时提供标题、概括与原文片段。

小结：
- 输入端：用户自由粘贴；
- 中间层：Agent 自动语义切块 + 概括 + 结构化；
- 存储端：entries 表只存“干净的自然块”，利于后续查询与向量检索。

## 7. 业务事实层与实时解析 / 批量审核

目标：将“原始文字流水 + RAG 层”与“可核算、可汇总的真实业务数据”解耦。所有内容先进入 entries 与 RAG 层，再通过 Agent 解析为结构化业务事实表，便于使用传统 SQL 做查询、汇算和审计。

### 7.1 三层关系回顾

- **层 1：原始素材 / 工作流记录（entries + RAG）**
  - 所有自然语言流水（笔记、对话、任务记录等）统一进入 `entries`；
  - 用于 RAG 召回、脑图、任务/项目/议题结构；
  - 已在前文通过 `entry_id + content + title_ai + summary_ai + structured_json + space_type + parent_entry_id` 等字段建模。

- **层 2：解释层（map_snapshots 等）**
  - 用地图/脑图快照的方式，表达“对 entries 的结构化理解”（战略图、局部项目图、难点拆解图等）；
  - 来自 Agent + RAG 的推导结果，可随时重算，仅少量版本长期保存。

- **层 3：业务事实层（真实业务数据）**
  - 请假、报销、借款、工资等**可核算、可结算**的业务事件；
  - 需要明确的字段（金额、日期、人员、项目、状态等），并且**可对账、可汇总、可审计**；
  - 通过语义解析，从 entries 中抽取结构化业务记录，写入专门的业务表。

总体思路：
- entries/RAG 层负责“理解”和“发现”；
- 业务事实层负责“结算”和“管理”。

### 7.2 库与 schema 组织建议

- 使用**同一 PostgreSQL 实例**，通过不同 schema 进行逻辑隔离：
  - RAG/entries 层：`public.entries` 以及向量相关表；
  - 业务事实层：位于 `biz`（或进一步细分为 `biz.hr`, `biz.finance`）等 schema 下；
- 好处：
  - 一个实例、一个连接串即可访问所有数据；
  - 可在必要时直接通过 `source_entry_id` 在跨 schema 查询时回溯到 entries；
  - 同时保持“知识/RAG 层”和“业务结算层”的职责边界清晰。

### 7.3 业务事实表的通用骨架

所有业务事实表推荐遵守一套**统一骨架**，再在此基础上加各自特有字段。

通用字段示意：

- **主键与来源追踪**
  - `id`：业务记录主键（`uuid` 或 `bigserial`）；
  - `source_entry_id`：来源于哪条 `entries.entry_id`，便于追溯原始文本/对话；
- **主体对象**
  - `employee_id` / `user_id`：对应的人/账号标识；
- **时间维度**
  - `biz_date`：业务发生日期（例如报销发生日期、请假起始日期等）；
  - `created_at`：写入业务事实表时间；
  - `updated_at`：最后更新时间；
- **金额/数量（如适用）**
  - `amount`：金额（报销、借款等）；
  - `currency`：币种；
- **分类与归属**
  - `category`：业务类型子类（例如：请假类型、费用类别）；
  - `project_code`：项目/工作流代码（若该业务与某个项目挂钩）；
- **状态与置信度**
  - `status`：状态流转字段，常见取值包括 `draft` / `ai_parsed` / `pending_review` / `confirmed` / `rejected` / `closed` 等；
  - `confidence`：AI 解析置信度（0~1），人工直接录入时可置为 1.0 或 NULL；
- **扩展字段**
  - `extra_json` (`jsonb`)：保留业务特有但尚未固定在表结构中的字段，方便迭代。

在此基础上，各业务表再追加自己的专有字段，例如：

- 请假（`biz.hr_leaves`）：`leave_type, start_date, end_date, days` 等；
- 报销（`biz.expenses`）：`invoice_no, vendor_name, tax_rate` 等；
- 借款（`biz.loans`）：`due_date, purpose` 等；
- 工资（`biz.payroll`）：`month, gross_amount, net_amount, tax_amount, payroll_cycle` 等。

### 7.4 实时解析 + 批量审核 + 人工核对流程

整体流程分为三个阶段：

1. **实时解析（Online Agent）**
   - 新的 entries 写入时：
     - Agent 判断该条记录是否包含某类业务事件（如请假、报销、借款、工资等）；
     - 如果是：
       - 从 `content` / `summary_ai` / `structured_json` 中抽取结构化要素；
       - 在对应的业务事实表（如 `biz.expenses`）中插入一条记录，填充通用字段与业务特有字段；
       - 设置：
         - `source_entry_id = entries.entry_id`；
         - `status = 'ai_parsed'`；
         - `confidence = <AI 计算的置信度>`；
   - 如判断不属于任何已知业务类型，则**仅停留在 entries/RAG 层**，不写入业务表。

2. **批量审核（Review Agents）**
   - 通过定时任务或触发机制，扫描业务事实表中：
     - `status IN ('ai_parsed', 'pending_review')` 的记录；
   - 针对每条记录，可由一个或多个 Review Agent 进行检查：
     - 规则检查（金额是否超阈值、日期区间是否合理、必填字段是否缺失等）；
     - 与原始 entries 文本的比对（看业务字段是否与自然语言描述一致）；
   - 审核结果可以：
     - 将高置信度、无明显异常的记录标记为 `status = 'confirmed'`；
     - 将存在疑点的记录标记为 `status = 'pending_manual'` 或类似状态，进入人工核对队列。

3. **人工记录核对**
   - 为人工提供一个“待核对业务记录”视图（技术上可由业务表 + entries 关联生成）：
     - 列表中展示业务事实字段及其当前状态、置信度；
     - 通过 `source_entry_id` 一键跳转到原始 entries 内容（包括上下文对话片段）；
   - 人工可对单条记录进行：
     - 修改业务字段（纠正 AI 抽取的错误）；
     - 确认：`status = 'confirmed'`；
     - 否决：`status = 'rejected'` 或设置作废标志；
   - 经人工确认后的记录，即可作为后续汇算、报表、对账的**最终可信数据源**。

### 7.5 与汇算/报表的关系

- 各类日常统计、报表、对账操作，一律基于业务事实表进行：
  - 例如：`SELECT SUM(amount) FROM biz.expenses WHERE biz_date BETWEEN ...`；
  - 或工资发放汇总：`SELECT SUM(net_amount) FROM biz.payroll WHERE month = '2025-12'`；
- 避免直接对 entries 做聚合运算，以免结果受文本解析波动影响；
- 如需追溯某一汇算数字的来源，可通过业务表中的 `source_entry_id` 反查到具体的 entries 记录和原始描述。

小结：
- entries/RAG 层：负责“记录一切”和“帮助理解”；
- 业务事实层：负责“存放已经结构化、可核算的业务事实”，支持传统 SQL 汇算与报表；
- 实时解析 + 批量审核 + 人工核对，保证了在引入 AI 自动解析的同时，仍能满足对账与审计需求。
